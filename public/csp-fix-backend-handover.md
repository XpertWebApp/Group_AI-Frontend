## 1. Why this doc exists

The Milestone 5 bilingual PDF preview (the Send Offer dual-pane modal) is broken on production. Both PDF panes render as broken-image icons. Console:

```
Framing 'blob:https://group-ai.s-e-t-t.com/...' violates the following
Content Security Policy directive: "frame-src 'self' https://www.googletagmanager.com".
The request has been blocked.
```

We initially diagnosed this as an nginx config issue. **We were wrong.** The CSP comes from **Helmet middleware running on the backend** (`src/app.ts:13`). This doc spells out:

1. What we missed and why
2. The exact one-file change needed on the BE
3. Why the change is safe
4. How to verify after deploy

---

## 2. What we missed (and why) — for the record

Yesterday's diagnostic run was:

> "Run a local production build of the FE and curl `localhost:3000` for CSP headers — if none appear, the FE is innocent and the bug is in nginx."

That test correctly showed the FE emits no CSP headers. The conclusion "the bug is in nginx" was wrong because:

- nginx on production routes `group-ai.s-e-t-t.com` traffic to **both** the FE Next.js process **and** the BE Express process
- The browser fetches the page HTML from the FE → no CSP on those responses → page loads fine
- But the iframe inside the page is loaded from a `blob:` URL **generated by an FE blob from a BE PDF response** — and that BE response carries Helmet's CSP header

The CSP layer we missed: `src/app.ts:13` has:

```typescript
app.use(helmet());
```

Bare Helmet with default config emits the CSP shown in the browser console verbatim. Specifically Helmet's default for `frame-src` is `'self'` (since v7), which forbids `blob:` URLs in iframes.

The client confirmed this independently by checking the nginx config — zero `add_header` directives in `/etc/nginx/sites-enabled/group-ai`, yet curl returned a CSP header. That's the smoking gun: the header was being emitted upstream, by Helmet, and passed through nginx untouched.

**Lesson learned for the doc:** when grepping for CSP, search **all Node services** sharing a hostname, not just the one the browser thinks it's hitting.

## 3. The change — one file, ~10 lines

### Current code (`src/app.ts`)

```typescript
import express, { Application } from 'express';
import helmet from 'helmet';
import cors from 'cors';
// ...

const app: Application = express();

// Security Middlewares
app.use(helmet());                  // ← the line to change
app.use(
  cors({
    origin: config.corsOrigin,
    credentials: true,
  })
);
```

### Replace with

```typescript
import express, { Application } from 'express';
import helmet from 'helmet';
import cors from 'cors';
// ...

const app: Application = express();

// Security Middlewares
//
// Helmet's default CSP forbids `blob:` URLs in iframes (`frame-src 'self'`),
// which breaks the FE's bilingual PDF preview modal — that modal renders
// each PDF pane as <iframe src="blob:..."> built from the BE's
// /actions/preview-pdf binary response. Same applies to <img src="blob:..">
// if we add PDF thumbnails later.
//
// `blob:` is a same-origin-only scheme — a blob URL can only reference
// content produced by JavaScript on the SAME ORIGIN. It is NOT a vector
// for embedding third-party content. Adding it to frame-src / img-src is
// safe and a common Helmet override.
app.use(
  helmet({
    contentSecurityPolicy: {
      directives: {
        ...helmet.contentSecurityPolicy.getDefaultDirectives(),
        'frame-src': ["'self'", 'blob:', 'https://www.googletagmanager.com'],
        'img-src':   ["'self'", 'data:', 'blob:'],
      },
    },
  })
);
app.use(
  cors({
    origin: config.corsOrigin,
    credentials: true,
  })
);
```

**That's the whole change.** No new dependencies, no new files, no other code touched.

## 4. Why this is safe

### 4.1 `blob:` is same-origin only

A `blob:` URL is created by JavaScript via `URL.createObjectURL(blob)`. The browser scopes the URL to the origin that created it. **A blob URL cannot reference content from another origin.** It cannot be used to:

- Load a third-party tracker
- Embed an attacker's iframe
- Smuggle data from another site

The only thing a `blob:` URL can do is reference data the page's own JavaScript already had in memory.

### 4.2 What we're allowing, concretely

After this change, the BE's CSP says:

- `frame-src 'self' blob: https://www.googletagmanager.com` — iframes can come from the same origin, blob URLs (always same-origin), or GTM
- `img-src 'self' data: blob:` — images can come from same origin, data URIs (already allowed), or blob URLs

Nothing else changes. The other Helmet defaults (`script-src 'self'`, `object-src 'none'`, `frame-ancestors 'self'`, etc.) stay locked down.

### 4.3 What we're NOT doing

- NOT removing Helmet
- NOT loosening `script-src` (the actually risky one)
- NOT allowing third-party iframes beyond GTM
- NOT changing `frame-ancestors` (clickjacking protection stays intact)
- NOT touching CORS / CSRF / HSTS — all other Helmet middleware stays on its defaults

### 4.4 OWASP / security-team review summary

> Adding `blob:` to `frame-src` and `img-src` is a routine override for applications that generate PDFs or images on the client side. Browsers enforce the same-origin scope of blob URLs at the URL-resolution layer; CSP enforcement is downstream of that. The Helmet maintainers explicitly document this override as the canonical fix for the bug we're hitting.

If your security review process wants a reference, the Helmet docs cover this pattern: https://helmetjs.github.io/

## 5. Verification after deploy

### 5.1 Confirm the CSP header changed

```bash
curl -sI https://group-ai.s-e-t-t.com/api/v1/health | grep -i content-security
```

Should now show:

```
content-security-policy: ...; frame-src 'self' blob: https://www.googletagmanager.com; img-src 'self' data: blob:; ...
```

Look for `blob:` in both `frame-src` and `img-src`. If either is missing, the BE didn't restart with the new code.

### 5.2 Confirm the FE preview works

1. Open any booking request → Send Offer button
2. The dual-preview modal opens
3. Both EN and DE PDF panes render the PDFs (not broken-image icons)
4. Browser console: no `Framing 'blob:...' violates...` errors

### 5.3 Negative test — confirm we didn't break GTM

If Google Tag Manager is in use (e.g. for analytics):
1. Open DevTools → Network → filter for `googletagmanager.com`
2. The GTM iframe should still load (it was in the original `frame-src`, we kept it)

### 5.4 Negative test — confirm we didn't loosen too much

```bash
curl -sI https://group-ai.s-e-t-t.com/api/v1/health | grep -i content-security
```

Check the full CSP value. The following should ALL still appear (unchanged from Helmet defaults):

- `default-src 'self'`
- `object-src 'none'`
- `frame-ancestors 'self'`
- `script-src 'self'`
- `script-src-attr 'none'`

If any of those are missing, we accidentally replaced the defaults instead of merging — the `...helmet.contentSecurityPolicy.getDefaultDirectives()` spread is critical and easy to miss in code review.

## 7. Why nginx is NOT the place to fix this

For completeness — in case the question comes up in review:

- nginx doesn't currently add a CSP header for this hostname (the client confirmed `/etc/nginx/sites-enabled/group-ai` has zero `add_header` directives)
- Even if it did, nginx adding `blob:` would be papering over the wrong layer — Helmet would still be sending the strict CSP from the BE, and the strictest CSP among layered headers wins
- The BE is the canonical source of the policy, so the BE is where the policy belongs
- Fixing it in nginx would require touching infra ops for every CSP change going forward; fixing it in code keeps the policy versioned with the BE deploy
