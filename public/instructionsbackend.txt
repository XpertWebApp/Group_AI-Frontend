Frontend: Role-Based Settings Visibility
How It Works
The login response (POST /api/v1/auth/login) already returns the user's role:


{
  "user": {
    "id": "uuid",
    "email": "admin@sett.ai",
    "firstName": "Admin",
    "lastName": null,
    "role": "ADMIN"
  },
  "tokens": {
    "accessToken": "...",
    "refreshToken": "..."
  }
}
The role field is either "ADMIN" or "USER".

The same role is also embedded in the JWT access token payload ({ id, email, role }), so you can decode it client-side if needed.

What to Do
1. Store the role after login

When the user logs in, store user.role alongside the tokens (in your auth context/store).

2. Hide the Settings nav item for Staff users

In the sidebar navigation, conditionally render the "Settings" link:


// Only show Settings for admin users
{user.role === 'ADMIN' && (
  <NavItem to="/settings" icon={SettingsIcon} label="Settings" />
)}
3. Protect the Settings route

Add a route guard so Staff users can't manually navigate to /settings via URL:


// Route guard component
function AdminRoute({ children }) {
  const { user } = useAuth();
  if (user.role !== 'ADMIN') {
    return <Navigate to="/dashboard" replace />;
  }
  return children;
}

// In your router
<Route path="/settings/*" element={<AdminRoute><SettingsPage /></AdminRoute>} />
4. Backend enforcement (already done)

Even if a Staff user somehow reaches the settings page, every /api/v1/settings/* endpoint returns:


{
  "success": false,
  "data": null,
  "message": "Admin access required",
  "error": "FORBIDDEN"
}
Status code: 403

Role Mapping Reference
role value	Display label	Settings access	All other pages
ADMIN	"Admin"	Full access	Full access
USER	"Staff"	Hidden / 403	Full access
Summary
Check user.role === 'ADMIN' to show/hide the Settings nav item
Add a route guard on /settings/* that redirects Staff to /dashboard
The backend already blocks all settings APIs with 403 for non-admin users — this is just the UI layer to match
